# 企画書の構成と書き方

## 1. 企画書の役割

企画書は、何を実現するのか、その価値は何か、どのように実行するのかを示し、採用・開発・予算などの判断につなげる文書である。検討過程をすべて記録するのではなく、判断に必要な情報を選んでまとめる。[1]

書式や章立ては提出先と目的に合わせて変える。新しいサービスの構想を評価する段階と、予算を承認する段階とでは、必要な具体性が異なる。構想段階でも実施範囲と検証方法を示し、予算承認の段階では担当者、期限、金額、算定根拠まで具体化する。

以下は、サービス企画に使いやすい基本構成である。特定の業界に共通する唯一の規格ではない。

## 2. 基本構成

| 項目 | 答える問い | 記載する内容 |
| --- | --- | --- |
| 企画概要 | 結局、何を提案するのか。 | 企画名、対象者、提供する体験、期待する価値。最初の一段落で全体像を伝える。 |
| 背景・課題 | なぜ取り組むのか。 | 対象者の不便・欲求、現在の代替手段、取り組む理由。調査事実とニーズの仮説を区別する。 |
| 対象者・提供価値 | 誰に、何がよくなるのか。 | 具体的な利用者像と利用場面。年齢や属性だけでなく、その人が達成したいことを書く。 |
| 企画内容 | どんな体験を、どう提供するのか。 | 利用の流れと主要機能。操作や場面を示し、初めて読む人が利用を想像できるようにする。 |
| 差別化 | 他の選択肢がある中で、なぜ選ばれるのか。 | 既存の代替手段と比較し、重点を置く体験や選ばれる理由を説明する。 |
| 実施計画 | どこまで、誰が、いつ、どの順序で実施するのか。 | 初期範囲、対象外、成果物、担当、段階、期限、次に進む判断条件。 |
| 費用・収益 | 何に費用がかかり、どう維持するのか。 | 初期費用と運用費、見積もりの前提。事業化を扱う場合は収益モデルと採算も示す。 |
| 効果・検証方法 | 成功したと何で判断するのか。 | 企画の目的に対応する指標、観察方法、評価時点。目標値には根拠を付ける。 |
| リスク・判断事項 | 何が実施を妨げ、何を決める必要があるのか。 | 主要な障害と対策、着手条件、承認を求める内容。 |

対象者・提供価値は「誰に、何を、どのように」を整理する事業コンセプトの考え方に対応する。[2] 実施計画では、必須・追加候補・対象外を分け、成果物や節目の責任を明確にする。[4]

各項目を必ず独立した章にする必要はない。短い企画なら統合し、重要な項目に紙幅を使う。分析フレームワークの表を埋めること自体を目的にしない。

## 3. 本文の書き方

### 冒頭で企画の中身を伝える

キャッチコピーは思想を伝えるために使い、直後にサービスの説明を置く。コピーだけで、何をするサービスなのかを読み手に推測させない。

例：

> Shelfieは、好きな本と装飾で自分だけの本棚を作り、自己紹介として共有できるアプリである。他人の棚で見つけた本を、自分の積読に迎えられる。

この段落から、利用者の行動とサービスの中心が分かるようにする。開発手段や調査の手順から書き始めない。

### 課題、機能、効果をつなぐ

機能の一覧を先に増やすのではなく、対象者の欲求に対して、その機能が何を可能にするかを書く。章をまたいでも、対象者や目標、費用の前提を変えない。文章で示す方針と数値計画の整合性も確かめる。[3]

例：

> 自分の趣味を文章だけで説明せずに伝えたい人に対し、選書と装飾を編集した本棚を提供する。その棚をプロフィールとして共有できるようにする。

「共有機能を付ける」だけでは、付ける理由も成功条件も伝わらない。

### 事実、仮説、提案を区別する

市場規模、競合の機能、調査結果などの事実には出典や確認日を付ける。検証していないニーズは「想定する」「仮説とする」と記す。開発方針は「提供する」「初期版に含める」と書き、実装済みの事実と混同しない。

ただし、文書全体が企画案であることを示せば、すべての節に「今回の提案」と付ける必要はない。必要な留保だけを、その判断に関わる箇所へ置く。

未定事項は空欄の一覧にせず、決める必要があるものに絞る。たとえば予算は、数値を作らず、見積もり対象と前提、いつ決めるかを示す。調査で分からなかったことと、企画として採用しないことは区別する。

### 読み手が判断できる粒度にそろえる

企画書には、主要な画面、利用の流れ、機能の優先順位、開発範囲を載せる。データベースの項目、API仕様、細かな例外処理などは、採否や費用の判断に影響する場合を除き、仕様書へ分ける。

背景やコンセプトは段落で説明し、比較・優先順位・費用は表にする。手順には番号を使い、順序のない並列事項には箇条書きを使う。書式の都合で、因果関係のある説明を細切れにしない。

### 記法と用語をそろえる

表題には企画名と文書種別を記し、必要に応じて日付、版、作成者を添える。本文は敬体または常体に統一し、一つの概念には同じ名称を使う。見出しは内容が分かる名前にし、階層を深くしすぎない。

Markdownでは、文書名を `#`、主要な章を `##`、必要な小節を `###` とする。太字は企画の定義や判断の要点に絞る。キャッチコピーや数値を繰り返して強調するより、機能と根拠を具体化する。

## 4. 本文に残す情報と、別資料へ分ける情報

| 本文に残す | 別資料へ分ける、または省く |
| --- | --- |
| 対象者、利用場面、解決する課題。 | 議論の時系列、発言者ごとの全発言。 |
| 機能の目的、優先順位、対象外の範囲。 | 思いついた案の全件列挙、採用に関係しない没案。 |
| 主要な制約、依存条件、実施リスク。 | 軽微な実装上の例外や操作ログ。 |
| 主張を裏付ける調査結果と出典。 | 資料をどう検索・取得したかという作業経緯。 |
| 費用・期限の前提、判断に必要な未決事項。 | 読み手の判断を変えない免責や注意書きの反復。 |

出典と作業経緯は別物である。競合比較や市場データの根拠は残すが、その資料を探した手順まで企画書に書く必要はない。

企画書は価値と実施方針、仕様書は詳細な振る舞い、事業計画書は収益・費用・資金を含む事業全体、議事録は検討経緯を中心に扱う。実務上は内容が重なるため、文書名だけで機械的に分けず、読み手の判断に必要かで決める。

## 5. 再利用できる骨組み

```markdown
# ［サービス名］企画書

［日付・版など、必要な基本情報］

## 1. 企画概要
対象者、提供する体験、価値を一段落で説明する。

## 2. 背景・対象者・課題
誰の、どの場面の、どの欲求に応えるかを示す。

## 3. サービス内容
代表的な利用シーンと、主要機能を説明する。

## 4. 差別化
代替手段と比較し、選ばれる理由を示す。

## 5. 実施範囲と計画
初期範囲、対象外、成果物、担当、期限を示す。

## 6. 費用・収益
費用の内訳と前提、維持・収益化の方法を示す。

## 7. 効果と検証方法
目的に対応する指標と確認方法を示す。

## 8. リスクと判断事項
主要なリスク、対策、着手や承認に必要な条件を示す。
```
